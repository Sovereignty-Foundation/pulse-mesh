# ADR-0011 — Envelope store layout version 2

**Status:** Accepted
**Date:** 2026-09-24
**Supersedes:** ADR-0008's body encoding and its answer to a held slot
**Amended:** 2026-09-24: a creator no longer zero-fills the region. A new object's pages come from the kernel zeroed, which is already an empty store (write cursor and busy-claim count zero, every slot's sequence word zero for "never written"), and on Linux the creator reserves the pages with `posix_fallocate` when it sizes the object, so an exhausted `/dev/shm` is `NoSpace` at creation rather than SIGBUS at the first touch of a page (SAF-14).
**Amended:** 2026-09-24: the capacity is the creator's choice (the daemon's `--store-slots`), and `EnvelopeStore::open_existing` attaches by name alone, taking the capacity from header bytes 16..20; an object still at size zero or with a zero magic may be a creator that has not finished, so it is retried for the budget `create_or_open` gives the same race before it is refused (SAF-20).
**Amended:** 2026-09-24: `EnvelopeStore::fetch_at(cursor, id)` reads the one slot a cursor names, under the same rule as `read_since`: the slot's sequence word must be the published value for that cursor before and after the copy, and the copy must be the verified envelope `id` names. Envelopes with the same content share an identifier whatever their origin, time or flags, so a reader told the cursor of the copy it wants reads that copy and no other; `fetch` still returns the first slot holding the identifier (SAF-24).
**Amended:** 2026-09-25: `open` and `open_existing` check the size and the header before they map anything. On Linux the header is read with `pread`, which reads a page the tmpfs never allocated as zeros instead of allocating it, and the store is mapped only once its magic is published; a creator publishes the magic only after it has reserved the pages, so an open never touches a page a full `/dev/shm` could not supply (SAF-44).
**Amended:** 2026-09-25: header bytes 32..40 hold an unlink token, an atomic `u64` that is zero in every store not being dropped; 40..64 stay zero. A creator's drop writes a random non-zero token there and reads the word back through the name, and unlinks the name only when its own token comes back, so an owner that exits after a successor has taken the name leaves the successor's store alone, as a ring's creator leaves alone a ring another has marked (ADR-0015). Readers ignore the word, so the layout version stays 2 (SAF-43).
**Amended:** 2026-09-25: a creator's drop unlinks the name straight after its token comes back, before it lets go of the descriptor, the header's mapping or the store's own mapping. POSIX has no call that removes a name only while it names a given object, and the open of the name fixes the object the token is read from, so a successor that unlinks the name and creates its store between that open and the unlink (an open and a `pread` on Linux; an open, an `fstat` and a mapping of the header on macOS) still loses its name. Within a hub the ring's mark keeps a successor away from the store's name until the drop is over (ADR-0015), so only a direct user of the store can meet that window. A creator can give the name up instead (`EnvelopeStore::disown`), and its drop then only unmaps: a hub whose ring another owner has marked does so, leaving the store's name to that owner (SAF-65).
**Amended:** 2026-09-25: within a hub the ring's mark keeps a successor away from the store's name for up to a second, the successor's wait (ADR-0015), not until the drop is over, so a hub stalled for longer than that between its open of the name and the unlink can still remove a successor's store, as a direct user of the store can. A hub that finds, before it lets its store go, that a new owner's ring has taken its ring's name gives the store's name up instead (SAF-82).

## Context

Layout version 1 (ADR-0008) wrote each envelope's body with `serde_json`. JSON renders a raw payload as an array of decimal numbers, about 3.6 bytes per byte of arbitrary data, so an envelope carrying more than about 18 KB of such a payload was refused with `EnvelopeTooLarge` by a 64 KiB entry: a 60 KB payload of varied bytes serialised to 219,020 bytes. The readers returned whatever parsed, without checking the envelope's content identifier.

A writer that dies between its odd and even marks leaves its slot's sequence word odd for good. Version 1 answered every later claim on that slot with `SlotBusy`, so the slot lost the envelope of every lap until the region was recreated.

## Decision

Version 2 keeps version 1's geometry: the 64-byte header, the 64-byte slot prefix with the sequence word at 0..8, the identifier at 8..24 and the body length at 24..28, bodies of at most 65,536 bytes from offset 64, and the sequence encoding (`0` never written, `2·lap+1` in progress, `2·lap+2` published, `lap = cursor / capacity`). `LAYOUT_VERSION` becomes 2, and the rest changes as follows.

The body is the envelope's canonical encoding, `PulseEnvelope::to_canonical_bytes()`, the cross-language form of chapter 3 of the specification, so the entry limit is the canonical size: an envelope with no type name and a raw payload carries up to 65,486 payload bytes. `EnvelopeTooLarge` reports the canonical size, and the `Serialization` error variant is removed because the encoding cannot fail.

The claim rule is unchanged. A writer for lap `L` claims its slot only by a compare-and-swap from an even value no newer than `2·L` to its mark `2·L+1`, and publishes with a release store of `2·L+2`. A claim never starts from an odd value, so no writer ever writes a slot another writer holds.

What changes is the answer to a failed claim. When the slot is held by another writer, mid-store or crashed, or already taken by a newer lap, the writer leaves it alone, gives up that cursor and takes a fresh one with another `fetch_add`, up to `CLAIM_ATTEMPTS` (four) cursors, and only then returns `SlotBusy`, naming the last cursor tried. Every failed claim is counted in header bytes 24..32, an `AtomicU64` that is zero when the region is created and that `EnvelopeStore::busy_claims()` reads; the count lives in the region so that every attached process sees the same value.

A reader trusts a slot only when its sequence word is the published value for the cursor it wants both before and after copying the body out; that SeqLock is what keeps a reader from returning a body while it changes. A reader now spends its read budget only on the writer of the cursor it wants (for `fetch`, the newest cursor handed out for the slot) and skips at once a slot held by an older lap's writer, because the wanted cursor's writer routes around a held slot instead of waiting for it. `read_since` skips such a cursor and continues, as it skips a lapped one.

As defence in depth against a copy corrupted or torn outside that protocol, whether by a process that writes the mapping directly, a bug or a hardware fault, a reader decodes its private copy with the canonical decoder (`decode_canonical_at`, the function behind `from_canonical_bytes`, which the fuzz target `fuzz_envelope_decode` exercises) and returns the envelope only if the decoder consumed exactly the recorded length, the decoded identifier equals the identifier recorded in the slot, and `verify()` holds. A slot that fails any of these holds no valid envelope: `fetch` continues its scan, and `read_since` skips the cursor. The checks are not the concurrency mechanism; the SeqLock is.

`open` refuses a version-1 region with `LayoutMismatch { field: "version", have: 1, need: 2 }`; its magic and size match version 2, so the version is where the mismatch shows. There is no migration. The daemon creates its objects afresh at every start (`PulseHub::create_fresh` unlinks whatever an earlier owner left), and an embedding process that meets a version-1 region removes it with `EnvelopeStore::unlink` and creates a new one.

Taking over a stale claim was considered and rejected. A claimant for lap `L` would have moved an odd mark `2·l+1` with `l + 2 <= L` to its own mark, every writer would then have published by compare-and-swap from its own mark, and a writer whose claim was taken would have received a `SlotStolen` error instead of moving the sequence word back. The age of a mark cannot tell a dead writer from a preempted one: at a high publish rate two laps pass in milliseconds, and a scheduler pause is enough. A writer that resumed after its claim was taken would keep copying into the slot and overwrite a newer envelope whose writer had been told `Ok`. Verification would catch only part of that, because the content identifier does not cover the origin, the timestamp or the flags, and a stale writer that rewrites the whole slot leaves a valid envelope of its own; fencing a stale writer out would need a writer lease that this layout does not have. Routing around a held slot gives up a slot instead of an envelope.

This record supersedes ADR-0008's body encoding and its answer to a held slot. ADR-0008's header, slot prefix, sequence encoding, claim rule and SeqLock reader rule stand, extended as above.

## Consequences

An entry now holds an envelope with up to 65,486 bytes of raw payload, against about 18 KB of arbitrary bytes before. Writing no longer runs a JSON formatter. Reading costs a canonical decode and one BLAKE3 hash of the content for each body a reader decodes, and no envelope is returned unverified. The writer does not hash, so an envelope whose identifier does not match its content, which only a caller that edits a constructed envelope's hashed fields can produce, is stored but never returned.

A writer that crashes mid-store holds its slot until the region is recreated. It loses its own envelope and no other: each time the ring comes round to that slot the claim routes to the next cursor, which costs a cursor and adds one to `busy_claims()`, and readers skip the cursor given up without waiting. The daemon recreates its store at every start, so in the daemon a crashed writer's slot is held only until the next start; an embedding process that keeps a region across crashes keeps the held slots until it recreates the region.

A preempted writer finishes its own store undisturbed, and the writers that meet its slot meanwhile route around it. If it publishes after the ring has moved more than a capacity past its cursor, `fetch` finds its envelope but `read_since`, which returns nothing older than the write cursor minus the capacity, does not. A reader that reaches a cursor given up after the slot's older holder has published cannot tell that cursor from one whose writer has yet to claim, and spends its read budget on it, as it always has on a claimed-but-unwritten cursor. Skipping a held slot at once loses an envelope only in a narrower case: when the wanted cursor's writer had not yet tried its claim, and the holder published before it did. The outcome then is the same as a read budget running out.

`store` returns `SlotBusy` only when every one of four cursors in a row lands on a held or taken slot, for example when both slots of a two-slot store are held. Under version 1 a single held slot failed one claim on every lap.

A version-1 region is refused rather than read. `PulseHub::create_fresh` never meets one, because it unlinks first; the constructors that attach to an existing store log the refusal and run without persistence, as they do for any refused region.
