# ADR-0015 — Ring header layout

**Status:** Accepted
**Date:** 2026-09-24
**Amended:** 2026-09-24: a creator no longer zero-fills the region; the kernel supplies a new object's pages zeroed, and on Linux the creator reserves them with `posix_fallocate` when it sizes the object, so an exhausted `/dev/shm` is an error at creation rather than SIGBUS at the first touch of a page (SAF-14).
**Amended:** 2026-09-24: bytes 44..48 hold a superseded flag, an atomic `u32` that is zero while the ring's writer uses it; 48..64 stay zero. The creator sets it as it unlinks the name when it drops, and the next owner of a hub name sets it on a ring left by an owner that died, before unlinking that name; it is set once, by compare-and-swap with release ordering, and a creator whose ring another has marked leaves the name, which may by then be a successor's, alone. A reader still mapped to a ring whose name is gone would otherwise poll it for ever: one that sees the flag has read every pulse the ring will hold, and `PulseHub::poll` reports it once so the application can reopen the name (`PulseHub::reopen`). The layout version stays 1, since a ring that never sets the flag reads as live (SAF-25).
**Amended:** 2026-09-25: whoever sets the flag decides the fate of the hub's names. The hub that created a ring (`PulseHub`) sets it first when it drops, then removes the envelope store's name and then the ring's; if another has set it, the hub leaves both names alone and gives its store's up (`EnvelopeStore::disown`, ADR-0011). The next owner of a hub name (`PulseHub::create_fresh`) unlinks a ring it finds only if its own compare-and-swap set the flag. A ring another has marked is left to that marker: the new owner waits for its name to go, for up to a second, before it touches the store's name, and unlinks the ring itself only after the wait, when the marker died between its mark and its removals or never removes names. Only a marker stalled for longer than the wait can still remove names the new owner has made by then (SAF-65).
**Amended:** 2026-09-25: a marker removes each of its names only while it is still its own. Before it lets its store go, and again before it removes the ring's name, it opens the ring's name: an unmarked ring there, or an object that is not a ring this build reads, is a new owner's, and the marker leaves the names to it; otherwise the store's name goes only if its unlink token comes back through it (ADR-0011), and the ring's only while a marked ring is under it. A marker stalled for longer than the wait now leaves the new owner's names alone, unless the stall falls between its open of a name and its removal of that name, a few system calls (SAF-82).
**Amended:** 2026-09-25: a reader loads the magic with relaxed ordering and follows the load with an acquire fence, which orders its reads of the other fields as an acquire load of the magic would. Off Linux an open reads the header through a read-only mapping, and std promises only relaxed atomic loads there (SAF-82).

## Context

`PulseRing` (`core/core-ring`) maps a 64-byte header followed by fixed-size slots. The header held the write cursor, the write count and the read cursor in bytes 0..24 and reserved zeros in 24..64, so nothing in the region said that it was a ring, how many slots it had or how large they were. `open(name, capacity)` checked only that the object was large enough for the capacity the caller named. A reader that named fewer slots than the creator mapped cleanly and indexed `cursor mod capacity` with the wrong modulus. A reader that named more was caught by the size check only where an object is exactly the ring's size, which holds on Linux but not on macOS, where a shared-memory object is rounded up to a page (16 KiB on Apple silicon): an open asking a 4-slot ring for 100 slots mapped it and indexed slots its creator never made. A region built with 192-byte version-2 slots and opened as 128-byte slots was mis-indexed from its second slot on. `pms ring inspect` and the MCP tool `mesh_ring_peek` had to guess: 1,024 slots for a raw name unless told otherwise, and the default hub's ring size for a hub name. `from_fd` zero-filled whatever region it was given with `init = true`, including a live ring the caller meant only to view.

## Decision

The reserved bytes describe the ring. Bytes 24..28 hold the magic `PMSR`, 28..32 the layout version (1), 32..40 the capacity in slots as a `u64`, 40..44 the slot size in bytes (128, or 192 for version-2 slots with a ready line), and 44..64 stay zero; every field is little-endian and is read and written as an atomic. The layout version numbers the header layout and is independent of the slot format, which the slot size records. A creator makes a new object and, on Linux, reserves its pages with `posix_fallocate` as it sizes it; the kernel supplies the pages zeroed, so the creator writes only the version, capacity and slot size, and stores the magic last with release ordering, as the envelope store publishes its header (ADR-0008), so a reader whose acquire load sees the magic sees a formatted ring. Every open checks the object's size first, as before, and then the header: magic, version, capacity and slot size, each mismatch refused with `RingError::LayoutMismatch { field, have, need }`. A zero magic may belong to a creator that has sized the object but not yet published its header, so an open re-reads it once a millisecond for fifty tries, the store's budget for the same race, before refusing it as `magic`. `PulseRing::open_existing(name)` maps the header alone, reads the capacity and slot size from it and then opens the ring as `open` does, so a reader need not know how the ring was made; `pms ring inspect` and `mesh_ring_peek` use it and drop their capacity option and parameter. `from_fd` and `from_fd_v2` let the header decide: a region whose magic is zero is fresh and is formatted with the caller's capacity and slot size, zero-filled first when `init` is set; a region that carries a header is validated against them and never zero-filled, whatever `init` says. On every error `from_fd` leaves the descriptor open and the caller's.

## Consequences

A ring created before this layout has a zero magic and is refused after the wait. No ring outlives the daemon that created it, so nothing migrates; a leftover object is unlinked by the next daemon started under its hub name, or by hand. An open with the wrong capacity or slot size is an error in both directions and on every platform instead of a silent mis-mapping; the size check keeps its precedence, so a request larger than the object is still `RegionTooSmall`, and `open(name, 0)`, which used to map a ring whose first publish divided by zero, is refused. `PulseHub::open` still maps the ring at its configured size, so a client configured with another ring size than the daemon's is refused rather than silently adapted; a caller that should follow the daemon can use `open_existing`. An MCP client that still sends `capacity` to `mesh_ring_peek` has it ignored. The publish and read paths are unchanged; an open costs a few header loads, plus about fifty milliseconds when the magic is zero, and `open_existing` maps the header on its own before it maps the ring. A `from_fd` caller that relied on `init = true` to reset a populated region must clear its magic or allocate a fresh region; none in the tree did. The header is not a lock: two `from_fd` calls formatting the same fresh region at once can both zero-fill it, so a region is formatted through one view before others are built over its descriptor.
